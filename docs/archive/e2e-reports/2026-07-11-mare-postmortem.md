- 输入：`D:\AICenter\neko\mare\mare.mp4`
- 状态：`DONE`

- 源字幕：943 行
- 语音分窗：61 个

## 2. 请求放大的实际构成

旧任务规划了 3 个翻译分片：

| 分片 | 行号 | 行数 |
| --- | --- | ---: |
| `c00000` | 1-399 | 399 |
| `c00001` | 400-780 | 381 |
| `c00002` | 781-943 | 163 |

第一片返回到第 321 行附近后提前结束，缺失的 322-399 共 78 行被旧逻辑逐行修复。实际翻译模型请求约 86 次：

| 用途 | 请求数 | 说明 |
| --- | ---: | --- |
| 术语候选提取 | 1 | staged bootstrap 第一步 |
| 术语候选整理 | 1 | staged bootstrap 第二步 |
| 主分片翻译 | 3 | 每个计划分片一次 |
| 分片后术语更新 | 3 | 旧配置每片一次 |
| 逐行修复 | 78 | 第一片缺失尾部逐行放大 |
| 合计 | 86 | 不含 ASR 请求 |

`events.jsonl` 中有 88 条旧 `provider_attempt`，比真实请求净多 2 条：staged 术语初始化的两次请求只记录了 1 条（少 1），3 个主分片又分别把请求开始和成功返回记成 2 条（多 3），相抵后净多 2。根因是事件没有表达请求生命周期；因此旧事件条数不能直接当 HTTP 请求数。

## 3. 已确认根因

1. 模型上下文与输出容量未知时，旧规划仍允许 399 行大分片，输出容易被截断。
2. 连续缺失 78 行被当作 78 个独立修复问题，没有批量恢复或请求放大上限。
3. 术语更新默认每个翻译分片调用一次；当保守分片增加时，请求数会随分片数线性增加。
4. `provider_attempt` 混合了请求开始与模型返回，UI 和日志无法给出可信请求总数。
5. 主窗口只轮播事件注释，没有稳定呈现术语、分片、恢复、质量和写出阶段。

## 4. 已完成修正

- 未知 token 容量使用最多 120 行的保守初始分片。
- 连续尾部缺失改为最多 120 行一组的批量补回。
- 单行修复最多允许 8 次；超过上限时触发自适应拆分，不再无限放大请求。
- 模型能力按模型保存上下文、输出预算、单批行数和思考档位。
- 术语更新默认每 3 个翻译分片合并一次；窗口后段失败时，先提交已经成功分片的术语更新。
- 请求生命周期区分 `started`、`completed` 和本地 `activity`；只有 `started` 累计模型请求。
- 请求统计覆盖术语初始化、分片翻译、术语更新、格式恢复、批量补回、单行修复、质量压缩和重排。
- 主窗口显示九阶段生产轨迹、分窗/分片计数、累计模型请求和当前恢复动作。
- 任务处理窗保留模型请求总数与分类制作摘要。

## 5. 同源离线重算

使用当前代码、当前桌面配置和旧任务的 943 行源字幕重新规划，不发起外部请求：

```text
planned_chunks: 8
chunk_sizes: [120, 120, 120, 120, 120, 120, 120, 103]
warning: Provider token capacity is unknown; using conservative chunk line limit
```

在没有重试和恢复的正常情况下，预计翻译模型请求为 13 次：

- staged 术语初始化：2 次
- 主分片翻译：8 次
- 每 3 片合并术语更新：3 次

若仍有一次尾部截断并成功批量补回，预计为 14 次。这个数字不是硬编码上限；网络重试、协议恢复、质量模型处理或自适应拆分后的子分片会增加请求，但任务处理窗会按用途解释增量。

## 6. 旧结果质量

- 字幕质量：`FAIL`
- 初始问题：时长过短 5、行数过多 1、阅读速度过高 1
- 残留问题：低于最小时长 5、低于 1 秒 28、超过最大时长 80、超过硬 CPS 1、行数过多 1
- SRT / ASS 交付检查：均为 `WARN`
- 两种格式均有 16 处视觉宽度超过硬限制，另有少量行数、堆叠高度和断行问题

这说明“任务成功生成文件”不等于“字幕已经达到可直接发布质量”。完成态必须保留人工审看提醒。

## 7. 真实复验标准

下一次用同一视频和同一模型运行时，至少核对：

1. 主窗口依次显示术语、8 个左右的翻译分片、质量和写出阶段，不再闪烁历史注释。
2. 任务处理窗的模型请求总数能由分类项相加得到，模型返回事件不重复增加计数。
3. 正常请求数应接近 13；出现恢复时必须明确显示恢复类型和增量原因。
4. `repair` 不得再次出现 78 次放大；单个失败分片的逐行修复不超过 8 次。
5. 输出必须继续生成 SRT / ASS，并重新审看专名一致性、超长字幕、极短时长和阅读速度。

真实 `gpt-5.6-terra` 复跑尚未自动触发，避免未经确认消耗外部额度。本报告的修复后请求数是基于当前规划和调用语义的可验证预期，最终以新任务 checkpoint 和 Provider 侧账单为准。
