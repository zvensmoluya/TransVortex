# TransVortex E2E 测试记录（2026-05-13）

## 1. 目的

本次测试的目标不是做理想条件下的最佳翻译演示，而是用一个真实日语动画样本对当前 TransVortex 端到端链路进行一次高强度现实测试，观察以下问题：

- 本地 ASR + 长视频切分 + 多轮翻译在真实机器上的可运行性。
- 现有 provider、memory、quality、export 链路在真实样本上的稳定性。
- 当前架构在时延、成本、编码兼容、字幕质量、一致性方面暴露出的真实问题。

本记录以客观现象和可复核证据为主，建议部分尽量克制，不在此阶段提前写成产品路线图。

## 5. 产物与编码问题

### 5.1 初次现象

现象：

- 在项目或编辑器中打开 SRT，中文正常。
- 在播放器中加载同一份 SRT，出现明显乱码。

原因定位：

- 文件本身是合法 UTF-8。
- 但导出的 SRT 没有 BOM。
- 部分 Windows 播放器或旧字幕解析器会将无 BOM 的 `.srt` 按 ANSI/GBK/Big5 猜测，导致中日文混合时出现乱码。

代码定位：

- [src/transvortex/formats/exporter.py](/d:/thevox/TransVortex/src/transvortex/formats/exporter.py)
- 原实现中 `export_srt()` 用 `encoding="utf-8"`。
- 同文件 `export_ass()` 已用 `encoding="utf-8-sig"`。

修复：

- 将 `export_srt()` 改为 `utf-8-sig`。
- 重新导出本次 E2E SRT。
- 文件头确认变为 `EF BB BF`。

对应测试：

- [tests/test_subtitle_quality.py](/d:/thevox/TransVortex/tests/test_subtitle_quality.py)
- 已新增 BOM 断言。

验证结果：

- 相关测试通过。
- 全量 `pytest -q` 通过。

## 6. 与内封繁中字幕的对比

### 6.1 参考字幕提取

提取路径：

```text
D:\AICenter\e2e\reference\Skymoon_Raws_ReZero_S04E05.ref.zh-TW.srt
```

注释轨：

```text
D:\AICenter\e2e\reference\Skymoon_Raws_ReZero_S04E05.annotation.zh-TW.srt
```

说明：

- 主参考轨约 28 KB。
- 注释轨仅一条内容，基本不参与正文对比。

### 6.2 对比限制

需要先说明两个限制：

1. 内封参考字幕来自人工精修的繁中字幕，不是日文原文字幕。
2. 我们的源文来自本地 ASR，因此文本切分、起止时间、语义合并方式与参考字幕天然不同。

因此：

- 不能将逐条文本相似度直接理解为“翻译模型质量得分”。
- 但可以把参考字幕当成高质量译文样例，帮助发现架构层问题。

### 6.3 可确认的差异

#### A. 术语不稳定

统计观察：

- 参考字幕中：
  - `昴` 出现 `10` 次
  - `愛蜜莉雅` 出现 `5` 次
  - `夏烏拉` 出现 `6` 次
  - `緹豐` 出现 `5` 次
- 我们的输出中：
  - `斯瓦尔` 出现 `4` 次
  - `斯巴鲁` 出现 `1` 次
  - `昴` 出现 `6` 次
  - `艾米莉娅` 出现 `1` 次
  - `爱蜜莉雅` 出现 `4` 次
  - `夏乌拉` 出现 `6` 次
  - `提丰` 出现 `4` 次

结论：

- 同一角色或专名在当前输出中会混用多个译名。
- 这不是单纯风格差异，而是一致性缺陷。
- `memory/conflicts.jsonl` 中也确实记录到了类似冲突。

示例：

```text
source: スヴァル / スバル
ours: 斯瓦尔 / 斯巴鲁 / 昴
ref: 昴
```

#### B. ASR 质量会直接传导到翻译

示例：

```text
SRC: すっからすかー? おっしゃーは 足になりしとしんすかー?
OURS: 斯巴鲁，是叫我吗？要我当脚力吗？
```

观察：

- 该源句本身已明显不自然，疑似 ASR 识别质量较差。
- 翻译模型只能在已有文本上做解释，不能恢复缺失的原始音频语义。

结论：

- 当前链路中，翻译质量受上游 ASR 文本质量强烈制约。
- 当 ASR 对专名、口语、角色说话方式识别不稳时，翻译端难以独立补救。

#### C. 时间轴与人工字幕切分差异显著

统计：

- 我们输出：`393` 条
- 参考字幕：`464` 条

观察：

- 我们字幕平均更短。
- 参考字幕更倾向将语义合并为较完整的阅读单位。
- 这会导致“逐条一一对应”的比较非常困难。

示例：

- 我们第一条从 `00:00:00,000` 开始。
- 参考字幕第一条从 `00:00:03,366` 开始。

这不一定表示整片整体错位 3.3 秒，也可能反映了：

- ASR 对无字幕空白区更敏感。
- 参考字幕刻意跳过无必要显示的口头声。
- 双方切分策略不同。

结论：

- 当前输出更接近“ASR 原始切句后轻度优化”的风格。
- 参考字幕更接近人工重编排后的最终播出字幕。

#### D. 文本层面并非全面失真

虽然整体逐条相似度统计较低，但从开头片段的人工对读看，许多句子的基本语义并没有错。

示例：

我们：

```text
出这题的人性格真差！
这本来就不公平啊！
不不不，你在说什么呢？
哪有人自己骂自己的啊！
```

参考：

```text
想出這題的人個性有夠差勁
這根本不公平吧
不不不不  你在說甚麼啊
為甚麼自己說自己壞話
```

结论：

- 纯句义层面，前段大量句子是“能对上意思”的。
- 但专名不稳定、切分风格不同、ASR 原文质量波动，使得最终产物和精修字幕的观感差距被明显放大。

## 7. Memory 相关观察

本次任务中 memory 产物实际生成并持续更新：

- `memory/translation_memory.json`
- `memory/memory_patches.jsonl`
- `memory/conflicts.jsonl`
- `memory/snapshots/`

观察：

- `memory_patches.jsonl` 明显增长，说明系统确实在每轮窗口后提取 memory。
- `conflicts.jsonl` 存在冲突记录。
- `consistency_issues.jsonl` 最终为 `0`。

这里暴露出的不是“memory 完全没工作”，而是更深一层的问题：

- memory 能发现冲突，
- 但这些冲突并没有阻止后续译名继续漂移，
- 最终产物中仍然保留了多套译名并存的状态。

这意味着当前 memory 更像“观察和记录机制”，还不是“产出强约束”的机制。

## 8. 本次测试中确认的缺陷

### 8.1 已确认的实现缺陷

1. `--detach --json` 启动成功但没有输出 JSON payload。
2. `status.updated_at` 在大量 progress 期间不刷新，容易给桌面端造成“任务静止”的假象。
3. progress 浮点未格式化，事件里会出现 `0.41000000000000003` 一类值。
4. `export_srt()` 初始未写 BOM，导致部分播放器出现乱码。

### 8.2 已确认的结果质量问题

1. 本地 ASR 对专名、口语和某些句段存在识别不稳。
2. 输出字幕切分偏碎，与人工精修字幕差距较大。
3. 术语一致性未被强约束，译名出现漂移。
4. 质量优化后仍有少量极短字幕和极高 CPS 残留。

### 8.3 尚不能下定论、但值得记录的点

1. 当前 `chunk_lines=8` 是否是性能/成本的主要瓶颈之一。
2. 大模型长上下文能力是否被现有切分策略明显低估。
3. `memory.patch.after_each_window=true` 在真实长视频上是否带来了过高的调用放大效应。

这些点从现象上看非常可疑，但本记录不将其提前定性为唯一根因。

## 9. 谨慎建议

以下建议仅作为测试后观察，不在本记录中上升为正式规划。

1. 在涉及角色名、组织名、地名、作品内术语时，术语系统需要比当前更强的约束优先级。
2. 对已有高质量字幕轨的媒体样本，应考虑支持直接走 subtitle-to-subtitle 对比或翻译链路，而不是强制先做音频 ASR。
3. 在长视频真实任务上，应重新评估当前翻译切分和 memory patch 的调用密度。
4. 质量报告目前能暴露异常，但离“自动收敛可播放字幕”的目标还有明显距离。
