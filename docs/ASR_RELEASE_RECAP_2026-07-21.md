# ASR 公开下载与安装体验复盘

日期：2026-07-21

这是一次临时现场复盘，正文集中记录本轮 faster-whisper 公开下载、安装器、卸载器和 Flutter 识别设置的观察。后续事项完成后，可将本文件归档或删除；产品长期边界仍以专题文档和 `CURRENT_BACKLOG.md` 为准。

## 现场结论

- Windows x64 的 faster-whisper runtime 已从公开 Release URL 下载，并按清单大小与 SHA-256 校验通过。
- 在全新的应用数据目录中下载 `small` 模型，安装后文件与固定 revision 一致。
- 下载后的受管 runtime 已在 CPU `int8` 下完成模型加载和本地转录探针。
- 最新内部 NSIS 安装包已生成，程序安装目录可以放在 D 盘；这不代表用户数据根也会自动迁移到 D 盘。
- 本轮验证通过的是后端安装管理器和本地探针；可见 Flutter 窗口中的点击安装、真实媒体任务和最终结果审看仍需单独完成。

## 路径语义

程序安装目录与用户数据目录是两条路径：

- 程序：用户在安装器中选择的 `TransVortex` 专用目录。
- 组件、模型、下载缓存、配置和任务：默认位于 `%LOCALAPPDATA%\TransVortex`。
- 临时验收可以通过 `TRANSVORTEX_HOME` 指向独立的 D 盘目录；普通用户界面目前还没有资源目录选择入口。
- 不应手动把组件目录搬进程序安装目录；如果要支持用户选择 D 盘，应实现独立的数据根设置和迁移语义。

## Flutter 识别设置观察

这些现象不代表 runtime 安装失败，而是设置页状态和产品表达需要收敛：

1. 安装 operation 进入终态后，页面仍保留完整进度条和“已完成”行。运行中显示进度；完成后应转为短暂结果提示；失败和取消才保留下一步动作。
2. operation 行增删后列表滚动位置没有复位，模型选择器和安装区域可能被截在中间。
3. 未发布的 NVIDIA 加速包仍显示灰色“安装”按钮。CPU-only 发布阶段应隐藏该动作，或明确显示“暂未开放”。
4. “组件已就绪”不能代替整条识别方案 readiness。runtime 已安装但默认模型缺失时，应明确提示还需要安装模型。
5. 选择 `small` 后仍显示已保存的 `large-v3` 默认方案属于草稿与已保存状态混在一起，界面需要更清楚地表达“尚未保存”。

## 现场新增观察：可见 APP 的操作语义与窗口安全感

这次从最新内部安装包进入可见 Flutter APP，重点观察 ASR 组件下载过程。结论是：当前主要问题已经从“能不能下载”转为“用户能不能确认下载正在发生、能不能安全地控制它”。这些不是单纯的美术问题，而是安装 operation、窗口生命周期和设置页状态没有形成一个可理解的闭环。

1. “准备”不是用户熟悉的动作名称。runtime 和模型都使用“准备”按钮，用户无法立即判断这是下载、安装、校验还是切换已有资源。按钮应明确表达实际动作，并区分“下载并安装”“使用已有模型”和“检查/修复”等不同语义。
2. 页面提供了“取消”，但现场没有形成可靠的取消闭环。用户无法确认取消请求是否已送达、后台任务是否真的停止、已写入的临时文件会如何处理，以及取消后是否可以再次安全发起下载。取消按钮不能只改变前端显示状态，必须与具体 operation 绑定并反馈最终结果。
3. 连续点击两个下载动作时，界面没有清楚呈现两个任务与后台 operation 的对应关系。用户看不出任务是并行、排队、去重还是互相覆盖，进度卡片也没有稳定的任务身份和独立状态，因此“点击了两个下载”与“实际发生了什么”之间出现断层。首版应先明确单任务/队列策略，并为每个可见任务显示稳定的名称、阶段、进度和结果。
4. 下载进行中关闭窗口缺少安全感。界面没有明确说明关闭后任务会继续、暂停还是取消，也没有在关闭前给出可恢复的选择；托盘菜单仍可能显示“空闲”，进一步削弱了用户对后台状态的判断。需要统一窗口关闭拦截、托盘状态、任务持久化和重新打开后的恢复语义。
5. 760×560 窗口中的信息层级仍然混乱：来源切换、模型/设备选择、准备清单、活动进度卡片和固定底栏同时争夺注意力，活动任务出现后静态配置没有退让，部分内容还会被截断。应把“当前活动任务”提升为主状态，静态配置收纳到次级区域，并保证操作按钮、进度和结果在同一可见层级内完成闭环。

本轮不应把这些问题归类为“再润色一下 UI”。在继续 Agent 接力入口或扩大 ASR 组件范围前，至少要先确定 operation 的取消、并发/排队、窗口关闭和恢复契约，再按契约重做设置页交互。

## 安装器与卸载器观察

- NSIS 安装器先解压到 `<InstallDir>.__staging`，校验后再切换到正式目录；`.__previous` 用于升级回滚。这是原子替换保护，不是把工作区直接复制给用户。
- 当前内部安装器显示逐文件解压详情，会暴露 staging 路径和 DLL 名称。功能正常，但公开版本应隐藏内部路径，改成产品化的安装进度文案。
- 卸载只删除程序目录、快捷方式和卸载注册信息，默认保留用户配置、任务、组件和模型；当前没有“同时清理用户数据”的选项。
- 卸载不会把程序目录移动到回收站，而是直接删除受管安装目录；用户数据保留策略与此分开。

## 当前发布边界

- 首轮只把 faster-whisper CPU runtime 作为已发布能力。
- NVIDIA 加速包仍未发布，不应在界面上呈现为可执行安装动作。
- 模型按固定 upstream revision 下载，不打进基础安装包。
- Agent 入口暂不提前开发；它应在原生点击安装和可见 APP 真实任务通过后，复用同一套安装能力。

## 待集中决策：第三方 ASR 依赖的责任边界

本轮后续讨论重新质疑了“所有 ASR 依赖都由 TransVortex 受管安装”的前提。以下只记录待决策方向，不视为已经生效的长期架构；它可能改变上文原生路线与 Agent 路线的推进顺序。

- 公开资产仓库适合托管 TransVortex 自己生成并定义协议的 faster-whisper runtime；重新打包并长期托管 NVIDIA 运行库或模型，可能把项目带回传统软件安装器的维护边界。
- NVIDIA 驱动应由用户通过 NVIDIA 官方渠道维护。CUDA、cuBLAS 和 cuDNN 可优先考虑由 Agent 复用已有环境，或在用户确认后从 NVIDIA 官方包源准备到隔离目录；TransVortex 负责探测、登记和诊断，而不是承诺修复任意机器环境。
- Whisper 模型可优先使用用户已有目录，或由 Agent 从上游固定 revision 获取。当前原生模型下载是否保留为便利选项，仍待集中决定。
- 不能只把当前 NVIDIA artifact URL 换成官方地址：现有清单、安装 operation、marker、readiness 和 Agent action 都假设“下载一个由 TransVortex 组织好的受管 ZIP”，若调整责任边界，需要一起修改契约和界面表达。
- 集中决策前不发布现有 NVIDIA ZIP，也不删除已经完成的 CPU runtime、模型下载或环境探针能力。

## 下一步顺序

1. 先定义并验证 ASR operation 的单任务/队列、取消、失败清理、窗口关闭和重新打开恢复语义。
2. 按上述契约重做设置页：明确动作文案，建立任务与进度的稳定关联，并简化 760×560 下的信息层级。
3. 修复终态进度条、列表滚动、readiness 文案和未发布组件动作，再用全新的 D 盘数据根完成 `small + CPU` 点击下载和真实媒体任务。
4. 决定是否提供普通用户可见的数据根选择，并补充迁移/清理语义。
5. 隐藏 NSIS 内部解压细节，完成安装器视觉和卸载说明的产品化；原生路线稳定后，再实现 Agent 的 apply/接力入口。

## 本轮采用的首版实施契约

- Flutter 将本机 Whisper 表达为一次“下载并启用”设置任务，不再要求用户分别点击运行组件和模型的“准备”。
- Local Service 全局只运行一个 ASR 设置或组件变更任务；同一任务幂等返回，不同任务明确拒绝，不使用界面不可见的伪并行。
- 设置任务按运行组件、模型、校验并启用三个阶段持久记录。关闭设置窗继续运行，托盘显示任务状态，重新打开后接回；明确退出应用时请求取消并等待安全终态。
- 取消或失败保留可校验的断点数据供重试复用，但不激活半成品安装目录。
- 首轮只开放 CPU：runtime 由 TransVortex 发布，模型从固定 upstream revision 获取或原地使用已有目录；NVIDIA / CUDA 不显示可执行安装动作。
