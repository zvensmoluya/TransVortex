# TransVortex 前端失败后开发准则

本文档只写禁令、停止条件和少量允许项。

它不是设计说明书，也不是实现教程。

## 1. 总则

旧 desktop 前端只保留一项价值：

> 证明后端对接可行。

旧 desktop 不再作为视觉参考、页面骨架参考、组件系统参考或风格参考。

后续前端必须先服从本规则，再谈设计、架构和实现。

## 2. 绝对禁忌

禁止把 TransVortex 做成：

- 通用后台管理台。
- SaaS 控制台。
- 开发调试面板。
- 普通 Web 应用。
- 左栏 + 顶栏 + 面板 + 列表的默认 Web 骨架。
- 页面级卡片网格。
- 圆角卡片套圆角卡片。
- Dashboard 式统计块。
- 用 badge、table、panel、card 拼出来的配置台。
- 组件库审美主导的界面。
- 调色后看起来更像“精致后台”的界面。

禁止把这些东西当作默认入口：

- 常驻左侧导航。
- 常驻顶部导航。
- 常驻面板墙。
- 常驻状态徽标墙。
- 常驻统计块墙。

禁止以下做法：

- 先建组件系统，再让设计服从系统。
- 先建 tokens，再靠调色找风格。
- 先拆 `Card`、`Panel`、`Section`，再想内容。
- 用圆角和阴影代替版式。
- 用纯文本、纯布局或纯 CSS 代替视觉资产。
- 用通用图标库决定产品气质。
- 用通用 React 组件库决定界面审美。

## 3. 注意力原则

设计意向高于工程惯性。

如果讨论开始围绕“这个 section 放哪里”“这个组件怎么复用”“这个 token 怎么命名”，而不是“这一屏给人的感觉对不对”，就说明方向已经偏了。

如果一张界面截图去掉产品名后仍像普通后台、SaaS 控制台或管理台，立即停止。

## 4. 设计顺序原则

TransVortex 前端不得从功能目录、页面清单、字幕流水线或旧 desktop 结构推导界面。

必须先建立强烈、具体、可执行的设计世界，再让功能进入这个世界。

功能不能以配置项、表格、面板、控制台模块的原形出现。

它们必须被转译成这个设计世界里的对象、空间、材质、动作和状态。

具体采用什么主题隐喻，属于后续设计文档的内容，不在本规则中预设。

如果实现开始从“这个功能需要什么页面/组件”出发，而不是从“这个能力在设计世界里应该以什么形态出现”出发，应立即停止。

## 5. 世界构建原则

TransVortex 前端不是游戏化，也不是把生产工具做成游戏。

但它可以借用游戏设计中的世界构建能力：先建立完整世界，再让界面、状态、动作和反馈服从这个世界。

设计世界不必来自字幕、翻译、桌面工具、专业软件或任何行业近邻。

从产品功能、行业对象或“专业工具应该长什么样”推导风格，也属于惯性。

不要追求显得专业。专业性不应被理解为后台、控制台、配置台、表格密度或行业软件习惯。

界面的最低要求是：用户能理解、能操作、能完成任务；状态可信，反馈清楚，失败可理解，操作稳定。

## 6. 圆角与卡片

圆角卡片布局默认禁用。

允许的圆角只限于：

- 输入框。
- 按钮。
- 浮层。
- 菜单。
- 轻量提示。
- 字幕片段、时间轴片段、选中态。

不允许把圆角容器变成页面默认设计单位。

## 7. 图标与视觉资产

通用线性图标库不得成为核心视觉语言。

核心图形、品牌标记、空状态和关键视觉符号必须服从 TransVortex 自己的设计判断，自定义 SVG、Canvas、CSS 图形或图片资产优先。

`lucide-react` 只能作为临时工具，不能决定产品气质。

SVG、无背景图片、局部插画、纹理、片段图形等资源不能等到“实现方便”才补。
它们必须在设计阶段被主动思考、主动创造、主动使用。

## 8. 技术边界

React、TypeScript、Tauri、service、adapter、state 这些工程结构可以保留。

但它们只能服务产品，不能反过来规定界面长相。

可用行为库，不用视觉库绑架审美。

TransVortex 前端目标平台是桌面 App，不是浏览器。

不提供浏览器使用路径，不以浏览器可用性作为验收标准。

不得把 Vite 端口页面当作产品界面验收对象。

调试和测试应优先通过 Tauri 桌面窗口进行；只有在排查构建、热更新或底层渲染问题时，才允许临时使用浏览器。

## 9. Tauri 原生客户端约束

Tauri 的 React/WebView 只作为自绘界面层使用。

不得因为 React、HTML、CSS、浏览器 DevTools 或 Vite 开发方式方便，就采用普通 Web 应用的产品模型。

后续实现必须像开发原生客户端一样约束自己：

- 主窗口是固定客户端工作面，不是浏览器页面。
- 主窗口不得使用页面路由、URL path、`window.history`、刷新页面或路径跳转作为产品导航模型。
- 主窗口不得出现常规 Web 站点式页面层级，例如首页、详情页、设置页、诊断页之间互相跳转。
- 主窗口不得把 `React state + position: fixed + backdrop + z-index` 当作默认弹窗方案。
- 制作单可以是主窗口固定 inspector 或独立 Tauri 子窗口；不得做成覆盖主窗口的网页表单 modal。
- 任务详情、事件、诊断、修复和高级设置应优先使用 Tauri 子窗口、系统对话框、固定 inspector 或明确的工具窗。
- 文件选择、目录选择等应使用系统原生 dialog。
- 允许轻量菜单、tooltip、popover，但它们只能依附于具体控件，不能承载任务详情、设置、诊断、修复等核心流程。
- 主窗口不做响应式网页适配；首轮按固定尺寸和固定区域设计。
- 不得使用 `@media`、`100vw`、`100vh`、大块 `overflow: auto`、滚动页面或流式自适应布局作为主体验基础。
- 不得用网页 hero、empty page、error page 的表达方式承载任务状态。
- 阻塞、失败、完成必须作为当前任务的状态呈现，而不是把整个窗口改成一张状态海报。

如果某个能力在原生客户端里更自然地表现为窗口、面板、检查器、系统 dialog 或任务状态条，就不得为了 React 实现方便把它压成主窗口内嵌网页 modal。

## 10. 兼容性边界

兼容性不得压制表达能力。

不得为了浏览器、窄屏、Web 习惯、通用响应式或跨平台一致性，把主体验降级成普通网页。

如果某个平台或设备要求牺牲 TransVortex 的主设计，应降级支持，必要时放弃该平台或设备。

## 11. 停止条件

以下情况出现任意一条，都应停止实现并回到设计判断：

- 页面像后台管理台。
- 页面像 SaaS dashboard。
- 页面像正常 Web 应用。
- 页面主要由卡片、面板、badge 和表格组成。
- 页面需要靠大量颜色微调才能“像设计”。
- 旧 desktop 的结构被自然复刻。
- 通用组件库开始主导气质。
- 为了兼容性牺牲主设计。
- 主窗口开始使用路由、页面跳转、URL path 或浏览器 history 组织产品。
- 任务详情、设置、诊断或修复被做成主窗口内嵌网页 modal。
- 失败状态被做成网页 hero、错误页或展示页。
- 固定尺寸客户端工作面退回响应式页面布局。

## 12. 允许项

允许先做一个真正的主工作面，再逐步补充辅助能力。

允许把服务接入、环境诊断、术语管理、导出设置做成 Tauri 子窗口、系统 dialog、固定 inspector、工具窗或任务状态条。

允许保留 React + TypeScript + Tauri 的实现方式。

## 13. 最终要求

TransVortex 前端必须先像一个完整、自洽、有强烈现实来源的设计世界，再像一个软件。

产品能力必须服从这个设计世界，而不是把设计世界压回行业软件惯性。

如果它首先像后台、像控制台、像配置台，那就是失败。
