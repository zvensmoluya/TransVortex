# TransVortex 前端设计风格说明

本文档记录 TransVortex 前端重设计的视觉和交互方向，面向产品、设计和前端实现协作者。它的目标是统一设计气质、主题元素和交互判断，让后续界面设计有清楚的出发点。

## 1. 核心定位

TransVortex 是一个低光字幕制作工作台。

核心气质是安静、专业、可检查、可恢复。
核心视觉来自字幕行、时间轴概览、质量状态、服务连接和输出文件。
深色环境服务于长时间工作，状态提示服务于任务理解。
温度来自清楚的反馈、稳定的流程和有秩序的资料组织，而不是装饰。

推荐主题：

```text
低光字幕制作工作台
```

也可以理解为：

```text
一个安静的字幕工坊
```

这里的“工坊”指一种清晰、有秩序、可以长期工作的创作环境。用户进入 TransVortex 后，应该感觉自己正在处理一个字幕项目：导入素材、接入模型、整理术语、检查字幕、修正问题，并把结果交付为字幕文件。

一句话描述：

```text
TransVortex 是一个安静、专业、有温度的本地字幕制作工作台。
```

这个方向需要同时满足三件事：

- 专业：用户愿意把视频、字幕、API key、模型配置和交付文件交给它处理。
- 可理解：复杂能力被转化成清楚的产品概念。
- 低压力：任务长、步骤多、状态复杂，界面稳定地说明当前进展和下一步。

## 2. 明确禁用的视觉方向

以下方向不作为 TransVortex 前端的视觉语言：

- 不用表情符号当作主要 UI 元素。
- 不做赛博风、霓虹风、机能风、黑客风。
- 不做多颜色渐变主视觉。
- 不做大面积彩虹渐变、紫蓝霓虹渐变、发光字效。
- 不做营销页式 hero 视觉。
- 不做“装饰先于信息”的界面。
- 不做以插画气氛替代真实工作区的首页。
- 不用注释性文字、说明书式段落或代码注释式提示代替界面设计。
- 不做大面积玻璃拟态、强透明、强模糊。
- 不做浮夸投影、强描边、强发光按钮。
- 不做卡片堆叠式杂乱布局。
- 不做以视觉噱头掩盖信息密度不足的设计。

如果某个视觉方案需要靠表情、强渐变、霓虹光、炫技背景、过度装饰或大段解释文字才能成立，说明它不适合 TransVortex。

### 2.1 视觉重设计约束

重新设计时不能只做“去装饰”。它必须建立一套更稳定的工作台视觉系统。

正向约束：

- **结构先于颜色**：页面层级必须主要靠布局、留白、字号、边线和对齐建立，而不是靠多种色块区分。
- **中性色优先**：界面 90% 以上应由中性背景、面板、文字和边线承载。强调色只用于当前焦点、主操作和关键任务状态。
- **状态色小面积使用**：成功、警告、失败、处理中只能出现在状态点、细线、图标、短标签或文字上，不应用作大面积背景。
- **单页单主强调**：一个页面默认只允许一个主强调色。不要在同一屏里同时让琥珀、青绿、蓝、红都成为视觉主角。
- **灰度也要成立**：如果把页面临时看成灰度，用户仍然应该能理解层级、当前焦点和主要操作。
- **工作区而不是卡片墙**：页面应像一个可长期工作的桌面工具区，而不是多个卡片平铺的后台面板。
- **面板有职责边界**：面板只用于清楚分隔工作区域，不用于把每个小信息块都包成卡片。
- **禁止卡片嵌套卡片**：重复项可以是行、列表项、表格行、时间轴片段，不应层层包 panel。
- **阴影默认不用**：阴影只用于浮层、modal、拖拽对象或需要脱离页面层的元素。普通页面区域用边线、背景层级和间距表达。
- **图标有等级**：导航、主要操作和少数状态可以使用图标；普通内容行不要为了装饰到处贴图标。
- **品牌标记要克制**：不要使用临时文字块、logo 占位符或强装饰品牌块。品牌感来自整体工作台秩序和状态反馈。
- **mock 数据像真实工作对象**：mock 页面应尽量呈现真实任务、字幕行、术语和服务状态，不要像演示用 dashboard。
- **少解释，多结构**：用明确分组、状态、控件和下一步操作表达含义，而不是用说明段落解释界面。

视觉 reset 的目标不是“更暗”或“更少颜色”，而是让界面重新变成专业、安静、可长时间使用的字幕生产工作台。

### 2.2 氛围主题硬约束

视觉品质不是锦上添花，而是 TransVortex 前端的验收门槛。

这里的“审美”不是装饰优先，也不是为了好看牺牲可读性。它指的是：界面必须准确传达“本地字幕生产工作台”的气质，让用户一眼感到这是一个可长期处理字幕项目的专业工具，而不是通用后台模板、SaaS 管理台或开发调试面板。

必须成立：

- 第一屏必须有明确的字幕生产工作台信号，而不是泛化的 dashboard。
- 用户应该能感到自己在处理字幕项目：素材、字幕行、时间轴、质量问题、术语、服务连接、输出文件这些对象要成为视觉骨架。
- 页面应该像一个有秩序的工作台，而不是多个卡片拼成的信息墙。
- 视觉应该安静但不空洞，专业但不冷冰，克制但不无聊。
- 所有页面应共享同一种工作台气质，而不是每个页面像不同模板拼接。
- mock 数据也必须服务主题，不能只填充“状态、统计、卡片、标签”。

明确不合格：

- 看起来像普通深色 admin dashboard。
- 看起来像参数配置后台。
- 看起来像模板化 SaaS 控制台。
- 看起来像单纯的“左侧导航 + 卡片网格”。
- 看起来像为了展示组件而堆出来的 demo 页面。
- 看起来缺少字幕、时间轴、检查、交付这些产品特征。
- 功能位置都在，但没有 TransVortex 的字幕生产气质。

视觉验收时应先问：

1. 这是不是一眼能看出是字幕生产工作台？
2. 它是否比通用后台模板更有产品识别度？
3. 它是否能支持长时间检查字幕，而不是只适合看一眼截图？
4. 它是否让字幕行、时间轴、质量问题、术语和输出文件成为主角？
5. 去掉颜色后，结构、层级和气质是否仍然成立？

如果一个方案功能完整但看起来无聊、模板化、没有字幕工作台气质，它仍然是不合格方案。

## 3. 主题风格

### 3.1 整体气质

关键词：

- 安静
- 专业
- 有温度
- 低光
- 工作台
- 检查
- 交付
- 可恢复
- 可检查

界面气质接近低光环境下的字幕制作界面：屏幕是主要工作面，核心对象是字幕行、时间信息、质量问题、模型连接和输出文件。整体感受应该沉静、可靠、适合长时间使用。

这个产品的“温度”来自清楚的状态、低压力的提示、可恢复的流程和有秩序的资料组织，而不是来自装饰。

### 3.2 色彩方向

基础色偏深、偏暖、偏稳定。

建议色彩：

- 背景：暖黑、炭灰、深石墨、暗橄榄灰。
- 面板：比背景略亮的哑光深灰。
- 文本：柔和白、浅灰、弱化灰。
- 主强调色：少量琥珀色、柔和青绿色或温和蓝色。
- 状态色：连接正常用青绿色，处理中用琥珀色，失败用克制红色，警告用暖黄。

色彩使用应以信息层级为中心。深色背景提供沉静的工作环境，暖色和青绿色用于提示关键状态，亮色只出现在需要用户注意的地方。

### 3.3 材质和层次

推荐材质感：

- 哑光面板。
- 细边线。
- 轻微投影。
- 柔和边缘高亮。
- 类似文件夹页签的结构。
- 时间轴概览里的比例和位置关系。
- 类似设备接口的连接状态。

材质服务于层级和手感。面板应该像稳定的工具板，时间轴概览用于定位字幕片段，术语表像可整理的项目资料，模型配置像可检查的服务接入口。

### 3.4 形状语言

建议：

- 卡片和面板圆角克制，优先 6px 到 8px。
- 工具按钮紧凑，常见操作优先使用图标。
- 字幕行、时间轴片段块、任务步骤使用稳定的矩形或轻微圆角。
- 重要状态用小灯、标签、细线和图标表达。
- 固定格式控件保持稳定尺寸，状态变化时界面位置稳定。

形状语言应偏工具化、秩序化。字幕行和时间轴片段块是核心形状，按钮、标签和状态提示围绕它们建立节奏。

## 4. 常见元素

TransVortex 的元素系统分两层：

- 核心功能元素：来自项目真实能力，直接出现在主要工作流里。
- 氛围物件元素：用于空状态、插图、局部背景、动效和品牌记忆点，帮助“低光字幕制作工作台”有可感知的灵魂。

这两层需要配合使用。核心功能元素保证产品可信和高效，氛围物件元素避免界面变成普通深色面板拼装。

### 4.1 核心功能元素

核心功能元素以项目真实能力和明确规划为依据。它们不是为了制造额外视觉故事，而是帮助界面把字幕生产流程表达得更清楚。

#### 字幕行

对应概念：

- 一行字幕。
- 当前编辑行。
- 翻译结果。
- 质量问题定位。

使用方式：

- 在结果检查页中作为核心对象。
- 在时间轴概览上作为字幕片段块。
- 在任务摘要中表示输出片段。
- 在空状态或插图中作为最基础的字幕符号。

设计要点：

- 字幕行清晰、可扫读、可选中。
- 当前行、问题行、已修改行、未导出行有稳定区分。
- 字幕行的外观保持朴素，让文字内容成为主角。

#### 时间轴概览

对应概念：

- 时间轴概览。
- 字幕开始和结束时间。
- 阅读速度和重叠问题。
- 视频和字幕的同步关系。

使用方式：

- 结果检查页的时间轴概览。
- 任务详情中展示当前处理进度。
- 质量检查中展示问题位置。

设计要点：

- 时间轴概览按字幕的 `start` / `end` 展示片段位置和长度。
- 它可以包含当前选中片段、问题标记和片段间隔。
- 时间轴帮助用户理解字幕位于视频中的位置。
- 问题标记可以连接到字幕列表和当前行编辑器。

#### 项目资料

对应概念：

- 术语表。
- 项目背景。
- 风格要求。
- 任务工件。
- 历史项目。

使用方式：

- 术语表工作区呈现为项目资料。
- 任务详情把工件分组为可理解的资料入口。
- 历史任务以项目方式组织，便于回看、恢复和重新导出。

设计要点：

- 项目资料可以通过页签、分组、标签和层级表达。
- 术语状态清楚区分：系统建议、已确认、锁定。
- 项目资料和任务输出保持关联，方便从任务跳转到术语、质量报告和输出文件。

#### 服务连接

对应概念：

- provider。
- API key。
- 翻译模型。
- ASR 服务。
- 主模型和备用模型。
- 连接测试。

使用方式：

- 模型与凭据页用“服务连接”表达模型配置。
- 普通模式展示服务商、key 状态、模型选择和测试结果。
- 专家模式承载 base URL、endpoint、mapping 等深层配置。

设计要点：

- 翻译模型和 ASR 服务使用不同分组。
- 连接状态可以用状态点、分组、线路关系和测试结果表达。
- API key 的保存位置和安全状态需要明确说明。

#### 质量状态

对应概念：

- 任务是否正常。
- 字幕质量问题。
- 连接状态。
- 是否需要用户处理。

使用方式：

- 青绿色：正常、已连接、可继续。
- 琥珀色：处理中、需要注意、非阻塞警告。
- 红色：失败、阻塞、必须处理。
- 灰色：未配置、未运行、不可用。

设计要点：

- 状态配合文字或图标使用。
- 警告和失败状态提供下一步操作。
- 状态颜色在所有页面保持一致语义。

#### 输出文件区

对应概念：

- 输出字幕文件。
- 重新导出。
- 交付结果。
- 已修改但未重新导出。

使用方式：

- 任务完成页显示输出文件区。
- 输出格式以多选方式展示：SRT、ASS、VTT。
- 每个输出文件提供打开、定位、重新导出。

设计要点：

- 保存编辑和重新导出是两个清楚的动作。
- 用户修改字幕后，界面显示“已修改但尚未重新导出”的状态。
- 输出文件路径、格式和更新时间清楚可见。

#### 任务流水线

对应概念：

- 输入素材。
- 获取源字幕。
- 翻译。
- 术语一致性。
- 质量检查。
- 导出交付。

推荐表达：

```text
输入素材 -> 源字幕 -> 翻译 -> 术语一致性 -> 质量检查 -> 导出
```

使用方式：

- 新建任务的步骤导航。
- 任务详情的进度状态。
- 失败恢复时说明从哪一步继续。

设计要点：

- 用户能看到当前步骤、已完成步骤和后续步骤。
- 每一步说明正在处理的内容。
- 恢复任务时展示将从哪个工件或阶段继续。

### 4.2 氛围物件元素

氛围物件元素可以更具象，但它们服务于感觉和记忆点，不替代真实功能。它们适合出现在首页空状态、任务完成页、引导页、文档配图、轻量背景纹理和生图资产里；核心工作区仍以真实控件和真实数据为主。

#### 暖色工作灯

暖色工作灯表达“安静、专注、正在制作”。它不是界面里的真实功能，而是低光工作台气质的来源之一。

可用位置：

- 首页或空状态的氛围图。
- 任务运行中的轻量背景光。
- 完成页的局部高光。

设计取法：

- 用暖色局部光强调当前工作区。
- 光感要柔和，服务于层级和焦点。
- 不需要画真实台灯，很多时候只需要暖色边缘光或局部高亮。

#### 字幕片段卡

字幕片段卡是“字幕行”的具象物件化表达，可以像一小段可移动、可检查的字幕片段。它比“纸条”更贴近产品事实，因为系统本身就围绕 segment 工作。

可用位置：

- 首页拖入素材后的任务摘要。
- 时间轴概览中的片段块。
- 空状态插图。
- 质量问题提示。

设计取法：

- 使用短横条、轻微圆角和弱阴影。
- 通过颜色或边线表达选中、问题、已修改、未导出。
- 让它看起来像字幕片段，而不是便签纸装饰。

#### 片库文件夹

片库文件夹表达项目资料、术语表、任务工件和历史记录。它能让“术语记忆”和“任务工件”更容易被理解为项目资产。

可用位置：

- 术语表空状态。
- 任务历史。
- 任务详情里的工件入口。
- 从任务导出术语 preset 的流程。

设计取法：

- 用页签、分组、文件夹轮廓和标签建立资料感。
- 文件夹可以作为小插图或图标，不需要把整个界面做成文件柜。

#### 服务插口

服务插口表达模型、API key、ASR provider 和连接测试。它把“配置 provider”这种抽象概念转成“接入服务”的动作。

可用位置：

- 模型与凭据页。
- 启动前检查。
- provider 测试结果。
- ASR 服务配置。

设计取法：

- 用端口、线路、状态点和连接关系表达服务状态。
- 翻译服务和 ASR 服务可以使用不同分组或不同接口样式。
- 插口只是隐喻，真实信息仍然是服务商、模型、key 状态和测试结果。

#### 检查灯

检查灯表达质量、连接和任务状态。它是最适合小面积复用的氛围物件，因为状态本来就是 TransVortex 的核心体验。

可用位置：

- 任务状态。
- 质量报告。
- provider 连接。
- 环境诊断。
- 字幕行问题标记。

设计取法：

- 小圆点、小灯条、细边线高亮都可以。
- 状态灯必须配合文字，不只靠颜色。
- 灯光感要克制，像工具状态提示，不像霓虹装饰。

#### 交付托盘

交付托盘表达输出文件、重新导出和成品交付。它让“导出 SRT/ASS/VTT”更像字幕制作流程的最后一步。

可用位置：

- 任务完成页。
- 输出文件区。
- 重新导出成功提示。
- 空状态或文档配图。

设计取法：

- 可以用托盘、文件叠层、输出槽等轻量图形表达。
- 真实界面中仍然要显示文件格式、路径、更新时间和打开按钮。

#### 项目标记

项目标记表达术语确认、风格要求、质量备注和人工修正。它提供少量“有人在整理项目”的感觉。

可用位置：

- 术语状态。
- 项目背景。
- 字幕行备注。
- 质量修复建议。
- 引导页提示。

设计取法：

- 使用标签、页签、角标、短注释。
- 标记服务于状态和归类，不能变成到处贴便签的装饰。

## 5. 页面风格建议

### 5.1 首页 / 新建任务

首页优先帮助用户开始一个字幕项目。

推荐感受：

- 像进入工作台。
- 明确邀请用户放入素材。
- 默认路径清楚，高级设置可展开。

推荐结构：

- 输入区域：拖入视频、字幕或 segments。
- 任务类型：转写并翻译、只生成源字幕、翻译已有字幕、重新导出。
- 快速设置：源语言、目标语言、输出格式。
- 检查区：模型连接、ASR 可用性、输出目录。
- 启动前摘要：说明将会执行的处理流程。

### 5.2 任务详情

任务详情是用户理解进度和处理失败的核心界面。

推荐感受：

- 像一个正在运行的制作线。
- 用户可以看懂当前状态。
- 技术日志作为辅助信息存在。

推荐结构：

- 任务标题、输入文件、目标语言、状态。
- 流水线步骤。
- 当前步骤说明。
- 进度和可恢复状态。
- 错误、警告和下一步操作。
- 输出和工件入口。
- 事件日志折叠区。

### 5.3 结果检查

结果检查是最专业、最高密度的工作区。

推荐感受：

- 像字幕审片台。
- 用户可以快速扫读、定位、编辑和重新导出。

推荐结构：

- 左侧或中间：字幕列表。
- 下方：时间轴概览。
- 右侧：当前行编辑、质量问题、术语一致性。
- 顶部：搜索、问题筛选、上一条/下一条问题、保存、重新导出。

设计要点：

- 行高、字体、对比度和键盘操作优先。
- 质量问题使用用户能理解的文案，例如“阅读速度过快”“时间轴重叠”“译文为空”。
- 当前行、问题行、已编辑行和未导出状态稳定可见。

### 5.4 术语表

术语表呈现为项目资料区。

推荐结构：

- 术语表列表。
- 条目列表。
- 条目详情。
- 状态筛选：系统建议、已确认、锁定。
- 从任务生成草稿。
- 从运行时术语库导出 preset。
- 一致性问题入口。

设计要点：

- 人工确认的术语有更高信任感。
- 系统建议和人工确认条目清楚分层。
- 锁定条目表达“固定译法”的含义。

### 5.5 模型与凭据

模型与凭据页像服务接入台。

推荐结构：

- 翻译服务连接。
- ASR 服务连接。
- API key 保存状态。
- 模型选择。
- 测试连接。
- 主模型和备用模型。
- 专家配置折叠入口。

设计要点：

- 默认凭据位置是用户级 `~/.transvortex/auth.json`。
- 凭据只显示保存状态和安全提示。
- 专家字段放在可发现但独立的区域。

### 5.6 环境诊断

环境诊断是修复入口。

推荐结构：

- Python、ffmpeg、ffprobe、faster-whisper、provider key、artifacts 权限。
- 阻塞问题和非阻塞问题分开。
- 每个问题提供下一步。
- 可配置项直接跳转到对应页面。

设计要点：

- 每个检查项说明影响的功能。
- 诊断结果转化为修复动作。
- 环境状态与新建任务的启动前检查联动。

## 6. 交互风格

### 6.1 渐进式配置

普通用户先看到必要选择，高级用户可以展开更多能力。

推荐模式：

- 默认流程展示核心选择。
- 高级设置分组展开。
- 专家配置进入独立区域。
- 启动前给摘要和阻塞检查。

示例：

```text
普通路径：选择视频 -> 选择语言 -> 选择模型 -> 开始
高级路径：展开字幕来源、ASR、术语表、质量处理、输出格式
专家路径：进入 provider mapping、endpoint、headers、token 字段
```

### 6.2 状态解释下一步

每个重要状态都回答三个问题：

- 当前发生了什么？
- 会影响什么？
- 用户能做什么？

示例：

```text
模型连接失败。当前任务无法开始翻译，请检查 API key 或服务地址。
```

配套操作：

```text
检查凭据
重新测试
查看详细错误
```

### 6.3 长任务有持续反馈

字幕任务可能持续很久。界面需要让用户知道系统仍在工作。

推荐：

- 显示当前步骤。
- 显示最近完成的动作。
- 显示可恢复性。
- 显示取消按钮。
- 重要日志折叠展示。
- 百分比、阶段和事件一起表达进度。

### 6.4 保存和导出分清

结果检查中有两个动作：

- 保存：保存用户对 segments 的编辑。
- 重新导出：根据当前 segments 生成 SRT/ASS/VTT 文件。

交互上需要明确：

- 已编辑但未保存。
- 已保存但未重新导出。
- 已重新导出。
- 导出文件路径和格式。

### 6.5 高密度区域优先效率

结果检查、术语表和任务历史是长期使用区域，交互效率优先。

推荐：

- 支持搜索。
- 支持筛选。
- 支持键盘跳转。
- 支持上一条/下一条问题。
- 支持稳定列宽和行高。
- 支持清楚的选中状态。

### 6.6 错误文案产品化

错误提示优先使用用户能理解的语言，再补充技术细节。

推荐结构：

```text
发生了什么：云端识别服务没有返回可用字幕。
影响是什么：这个任务暂时无法进入翻译步骤。
下一步：检查 API key、换用本地识别，或查看 ASR 诊断。
技术详情：...
```

技术详情放在折叠区域，主提示聚焦影响和下一步。

## 7. 文案风格

文案应自然、清楚、具体。

前端文案应该直接服务于用户行动和状态理解，不应该像代码注释、功能说明书或开发者备注。

允许出现：

- 当前状态，例如“正在翻译字幕”。
- 影响说明，例如“缺少 ffmpeg，无法从视频提取音频”。
- 下一步操作，例如“安装 ffmpeg 后重新检测”。
- 明确字段标签，例如“目标语言”“输出格式”“重新导出”。

不应该出现：

- 解释界面本身的注释，例如“这里用于显示任务状态”。
- 解释实现细节的文字，例如“该字段会传给 worker 的 source_mode 参数”。
- 用长段说明替代控件层级、空状态、状态标签或操作按钮。
- 在普通界面中出现类似代码注释的说明，例如“// 选择 provider 后会刷新模型列表”。

如果必须解释复杂能力，应优先通过更清楚的分组、标签、状态和下一步操作完成，而不是堆放一段说明文字。

推荐用法：

- “创建字幕任务”
- “选择字幕来源”
- “识别音频”
- “翻译字幕”
- “检查字幕质量”
- “重新导出”
- “服务连接”
- “项目术语表”
- “系统建议的术语”
- “已确认术语”
- “锁定术语”

内部实现名可以出现在专家模式、日志或开发者文档中。普通界面优先使用用户能理解的概念，再在必要时补充真实配置名或字段名。

## 8. 图标和视觉资产

### 8.1 图标

图标服务于识别和操作效率。

建议映射：

- 视频输入：film 或 video。
- 字幕行：captions 或 text。
- 时间轴：timeline 或 ruler。
- 术语表：folder、book、tags。
- 模型连接：plug、server、network。
- 凭据：key。
- 质量检查：check circle、alert triangle、gauge。
- 导出：download、package、tray。
- 重新导出：refresh + export。

图标按钮配 tooltip，尤其是结果检查和专家配置区域。

### 8.2 生图资产

生图适合用于：

- 设计方向探索。
- 官网或文档配图。
- 空状态氛围图。
- 引导页。
- 非核心工作区的小型插图。

生成图的主题可以围绕：

- 低光字幕工作台。
- 字幕行和时间轴概览。
- 项目资料区。
- 服务连接状态。
- 质量状态。
- 输出文件区。
- 暖色工作灯。
- 字幕片段卡。
- 片库文件夹。
- 服务插口。
- 检查灯。
- 交付托盘。

核心工作界面仍以真实控件、真实状态和可编辑内容为主。生图资产负责提供氛围，产品界面负责完成任务。

前端生图统一使用 `$zven-imagegen` skill 和 `docs/FRONTEND/FRONTEND_IMAGE_PROMPTS.md` 中的模板。生图结果只能作为视觉探索、空状态或文档配图参考，不能替代真实 React/CSS 界面实现。

## 9. 可落地的设计判断

当一个设计方案拿不准时，可以用下面的问题判断：

- 它是否让用户更清楚自己在处理一个字幕项目？
- 它是否把复杂能力转成了可理解的对象或动作？
- 它是否支持长时间检查大量字幕？
- 它是否能清楚表达任务进度、失败原因和恢复路径？
- 它是否让普通用户安心，同时让高级用户能找到深层能力？
- 它是否能被复用到多个页面，而不只是单张概念图？

这些问题帮助设计保持在“字幕制作工作台”的主线上。

## 10. 简短设计准则

- 以字幕制作工作台作为主隐喻。
- 用字幕行、时间轴概览、项目资料、服务连接、质量状态和输出文件区建立功能骨架。
- 用暖色工作灯、字幕片段卡、片库文件夹、服务插口、检查灯和交付托盘建立氛围记忆点。
- 深色环境服务于长时间工作和信息聚焦。
- 温度来自清楚状态、柔和反馈和可恢复流程。
- 品牌感体现在任务流动、处理状态和交付体验中。
- 复杂能力采用渐进披露。
- 错误状态给出影响和下一步。
- 结果检查保持高效、稳定、可长期使用。
- 保存和导出严格区分。
- 所有主题元素都对应真实产品概念。
