# TransVortex 前端核心方向

> 归档说明：本文档属于 2026-05 产品方向与架构治理过载阶段。它保留部分产品判断价值，但不再是当前有效规范。后续前端重建优先遵守 `../../rules/FRONTEND_FAILURE_RECOVERY_RULES.md`。

本文档定义 TransVortex 前端的长期产品方向、核心对象和体验边界。

它不定义阶段任务，也不决定第一版砍掉哪些能力。旧阶段计划已归档，新的阶段拆分必须先遵守 `../rules/FRONTEND_FAILURE_RECOVERY_RULES.md`。这里要回答的是：

> TransVortex 前端最终应该成为什么，以及无论分几步实现，都不能偏离哪些产品骨架。

核心判断：

> 不要做“参数表驱动的工具界面”，而要做“字幕生产工作流驱动的本地专业工作台”。

TransVortex 不应该长成普通的“一键视频转字幕”玩具，也不应该长成把 CLI、worker、provider、artifact 全部摊开的开发调试面板。它更准确的定位是：

> 面向字幕生产的本地桌面工作台：低门槛创建任务，高可控检查结果，专业用户可以深入调试模型、术语和交付质量。

实现可以逐步推进，但产品骨架不能临时搭。即使第一阶段只实现有限能力，也应该先站在最终工作台的结构上，而不是先做一个上传表单、日志窗口和下载按钮，后面再把任务详情、结果检查、术语表和 provider 管理补在错误的位置。

## 1. 产品终局

TransVortex 前端的终局不是“可视化 CLI”，而是一个小型字幕生产站。

它应该覆盖一条完整字幕生产链路：

```text
创建任务
  -> 运行任务
  -> 观察进度
  -> 处理失败
  -> 检查字幕
  -> 修正问题
  -> 管理术语
  -> 重新导出
  -> 沉淀项目资产
```

这条链路里，用户关心的不是某个底层参数是否被传给 worker，而是：

- 我输入了什么？
- 系统现在做到哪一步？
- 使用了什么字幕来源和模型服务？
- 失败在哪里？
- 失败后能不能恢复？
- 结果在哪里？
- 质量有没有问题？
- 我能不能改完重新导出？
- 术语和风格能不能在后续任务中复用？

前端的职责是把复杂能力组织成这些用户可理解的问题和动作。

## 2. 核心体验结构

TransVortex 应该采用三层体验结构：

- **快速任务层**：让普通用户能拖入视频或字幕，选择语言、字幕来源、模型和输出格式，然后开始任务。
- **专业检查层**：让字幕制作者检查质量问题、编辑字幕行、处理术语一致性，并重新导出交付文件。
- **专家配置层**：让高级用户管理 provider、模型路由、ASR 参数、环境诊断和工件日志。

这三层不应该混在一个大表单里。

当前 TransVortex 的能力已经很复杂：ASR、字幕轨提取、翻译、术语记忆、repair、compress、reflow、质量报告、SRT/ASS/VTT 导出、provider routing、任务恢复。前端如果把这些能力全部平铺出来，用户会被内部概念压垮。

所以设计原则是：

> 默认流程简单，问题出现时解释清楚，高级能力可发现但不干扰主流程。

## 3. 任务是中心对象

TransVortex 的基本单位不是模型、不是文件、不是 provider，而是一个字幕生产任务。

任务应该成为所有页面、状态和工件的组织中心：

- 输入文件
- 源语言和目标语言
- 字幕来源
- ASR 方式
- 翻译模型
- 当前状态
- 质量问题
- 输出文件
- 可恢复性
- 工件入口
- 结果检查入口

用户不应该在多个功能页之间猜结果在哪里。任务详情页应该成为中枢：进度、失败、输出、日志、恢复、检查结果都从这里串起来。

这不意味着所有东西都只能藏在任务详情里。结果检查、术语表、模型与凭据可以有独立入口，但它们必须和任务建立清楚关系，而不是变成互不相干的工具页。

## 4. 结果检查属于主流程

结果检查不是任务完成后的附属功能，而是 TransVortex 区别于普通“视频转字幕工具”的核心体验。

很多工具只做到“生成文件”。TransVortex 的价值链更长：

1. 生成字幕。
2. 检查质量。
3. 修改字幕。
4. 检查术语一致性。
5. 重新导出。

所以结果检查应该被当作专业字幕工作台设计，而不是“打开 JSON 文件”或“查看导出文本”。

结果检查的核心对象是字幕行，也就是结构化 `Segment`。它必须支持用户围绕字幕行完成：

- 搜索和筛选字幕。
- 定位质量问题。
- 跳转上一条 / 下一条问题。
- 编辑原文、译文和时间。
- 查看术语命中和疑似不一致。
- 理解当前修改是否已保存。
- 理解导出文件是否已更新。
- 重新导出 SRT、ASS、VTT。

字幕结果的真实来源是结构化字幕行。SRT、ASS、VTT 是导出视图，不是产品内部的唯一真相。

## 5. 质量问题必须可操作

字幕质量问题不应该只是一个 report 文件，也不应该只显示内部 issue code。

前端应该把质量问题变成可点击、可筛选、可跳转、可处理的对象。

例如：

- 阅读速度过快。
- 译文为空。
- 时间轴重叠。
- 单行过长。
- 双语字幕拥挤。
- 术语疑似不一致。
- 持续时间过短。
- 格式导出风险。

每个问题都应该回答：

- 发生了什么？
- 会影响什么？
- 用户能做什么？

内部可以保留 `CPS_TOO_HIGH` 这样的 code，但普通界面应优先显示用户语言：

| 表达方式 | 示例 |
| --- | --- |
| 不好 | `CPS_TOO_HIGH` |
| 较好 | 阅读速度过快，观众可能来不及看完 |

质量问题的下一步可以是手动编辑、自动优化、跳过、重新导出或查看原因。报告文本只是辅助，导航和处理才是核心。

## 6. 术语记忆是项目资产

术语记忆是 TransVortex 的核心差异化能力。它不只是“给 prompt 加一段词表”，而是长期字幕生产资产。

前端应该把术语记忆表达成项目术语表，而不是一个任务表单里的 `preset id`。

用户需要理解的是：

- 哪些术语来自人工维护。
- 哪些术语是系统建议。
- 哪些术语已经确认。
- 哪些术语被强制固定。
- 哪些字幕行疑似违反术语表。
- 本次任务是否产生了可沉淀的新术语。

推荐术语状态使用用户可理解的三类：

| 内部状态 | 前端表达 |
| --- | --- |
| `proposed` | 系统建议 |
| `confirmed` | 已确认 |
| `locked` | 强制固定 |

术语条目应该逐步具备这些信息：

- 源词。
- 目标译法。
- 类型：人名、称呼、术语、作品名、ASR 纠错、固定短语。
- 状态。
- 适用范围。
- 备注。
- 相关字幕行。

即使某个阶段还没有完整术语资产管理系统，也不应该把术语能力降级成一个隐藏参数。前端信息架构应始终把它当作项目资产来安放。

## 7. Provider 是服务连接体系

Provider 和模型配置也是 TransVortex 的核心能力，但普通用户不应该先面对 base URL、endpoint、request mapping、response mapping、token 字段等内部配置。

前端应该把 provider 表达成“服务连接”：

- 选择服务商。
- 保存 API key。
- 选择模型。
- 测试连接。
- 设置默认模型。
- 设置备用模型。
- 任务失败时理解是不是服务连接问题。

同时，翻译模型和 ASR 服务必须视觉上分开。

用户容易混淆：

- 翻译模型 provider。
- ASR 云端 provider。
- 本地 ASR。

所以前端应该拆成两块：

- **翻译服务**：OpenAI、Anthropic、Google、兼容网关、自定义 provider。
- **语音识别服务**：本地 faster-whisper、OpenAI Transcriptions、后续其他云端 ASR。

专家配置不能消失，但应该进入独立区域，承载 base URL、endpoint、auth、headers、request mapping、response mapping、limits、fallback 等深层能力。

API key 的保存位置需要说清楚：

> API key 会保存到用户级凭据文件，不会写入当前项目目录。

这既是安全语义，也是用户信任的一部分。

## 8. 保存和导出必须分清

字幕产品里最容易混乱的地方，是把“保存编辑”和“导出文件”混成一个动作。

TransVortex 必须明确区分：

- 保存：保存用户对结构化字幕行的修改。
- 重新导出：根据当前字幕行生成 SRT、ASS、VTT 文件。

状态也应该清楚：

- 未修改。
- 有未保存修改。
- 已保存，待重新导出。
- 已重新导出。
- 导出失败。

输出格式应该用多选表达：

- SRT。
- ASS。
- VTT。

不要让 `both` 这类内部值成为用户理解交付结果的方式。

## 9. 内部概念必须翻译成用户概念

很多 worker/CLI 概念不应该直接出现在普通界面里。

| 内部概念 | 前端应该表达成 |
| --- | --- |
| `source_mode` | 字幕来源 |
| `input_type` | 输入类型 |
| `checkpoint` | 可从上次进度继续 |
| `bootstrap` | 自动提取术语草稿 |
| `inject` | 翻译时参考术语表 |
| `patch` | 从本次翻译中更新术语建议 |
| `delivery report` | 输出质量检查 |
| `provider routing` | 主模型 / 备用模型 |
| `artifact directory` | 任务文件夹 / 诊断文件 |
| `segments` | 字幕行 / 结构化字幕结果 |

内部名可以出现在专家模式、日志和开发者文档中，但普通界面要先使用用户能理解的产品语言。

这不是简单的翻译问题，而是产品语义问题。例如：

- “启用术语记忆能力”不等于“启用整个 memory 子系统”。
- “用户选择的预设术语表”不等于“模型运行时自动积累的术语库”。
- “provider 可配置”不等于“用户需要理解所有 provider schema 字段”。

前端要让用户理解结果和影响，而不是让用户学习内部实现。

## 10. 环境诊断是修复入口

环境诊断不要只是显示：

- `ffmpeg: missing`
- `python: ok`
- `provider: failed`

它应该说明影响和下一步。

例如 ffmpeg 未找到：

- **影响**：无法从视频提取音频或字幕轨。
- **下一步**：安装 ffmpeg、重新检测，或打开设置。

诊断结果应该分成三类：

- **阻塞问题**：不修复无法开始任务。
- **质量风险**：可以运行，但结果可能变差。
- **可选增强**：有则更好，没有也能运行。

这样用户能知道什么必须处理，什么可以先忽略。

环境诊断还应该和新建任务的启动前检查联动。用户不应该开始任务后才发现缺 key、缺 ffmpeg 或 ASR 服务不可用。

## 11. 推荐信息架构

以下产品区域仍然成立，但它们不等于必须做成常驻左侧导航或 Web 多页面：

- 新建任务。
- 任务历史。
- 结果检查。
- 术语表。
- 模型与凭据。
- 环境诊断。
- 设置。

结果检查的数据归属任务，但入口不应被任务历史完全埋住。

更理想的关系是：

```text
任务历史 -> 任务详情 -> 检查结果
```

同时提供“继续检查最近任务”或“结果检查”的快捷入口。这个入口可以是任务切换器、命令面板、浮层、最近任务抽屉或其他桌面应用方式，不应默认退回“左栏导航 + 页面切换”的 Web 结构。

术语表、模型与凭据、环境诊断虽然有独立页面，但它们不应该变成孤立后台。它们应该能从新建任务、任务详情、失败状态和结果检查中被自然调用。

## 12. 核心页面职责

### 新建任务

新建任务不应该是参数长表单，而应该是面向字幕生产路径的任务创建流程。

它至少要让用户在开始前理解：

- 输入是什么。
- 字幕来源是什么。
- 是否会执行 ASR。
- 使用哪个翻译服务。
- 是否使用术语表。
- 会生成哪些输出文件。
- 是否存在阻塞问题。

### 任务详情

任务详情是用户理解进度和处理失败的中枢。

它必须承担这些职责：

- 展示任务当前阶段。
- 展示正在处理的动作。
- 展示进度和可恢复性。
- 解释警告和错误。
- 提供取消、恢复、查看日志、打开输出、检查结果等入口。
- 把工件包装成用户可理解的入口，而不是直接暴露目录树。

失败状态尤其重要。失败页不应该只说“任务失败”，而应该说明：

- 失败阶段。
- 失败原因。
- 是否可恢复。
- 推荐操作。
- 相关日志入口。

### 结果检查

结果检查承担字幕审校、质量定位、人工编辑和重新导出。

它应该是高密度、高可读性、支持长时间工作的专业界面。字幕列表、当前行编辑、质量问题、术语提示、时间轴概览和输出状态需要联动。

### 术语表

术语表承担项目资产管理，而不是简单参数选择。

它应该逐步支持查看、确认、锁定、导入、导出、从任务沉淀术语，以及从术语问题跳回相关字幕行。

### 模型与凭据

模型与凭据承担服务连接管理。

它应该优先让用户完成服务商选择、API key 保存、模型选择、连接测试、主模型和备用模型设置。专家字段要可发现，但不应污染普通流程。

### 环境诊断

环境诊断承担修复入口。

它应该告诉用户哪些问题阻塞任务，哪些只是质量风险，哪些是可选增强，并提供明确下一步。

## 13. 视觉方向

TransVortex 不适合做成轻浮的消费级工具，也不适合做成 IDE 式的完全工程化界面，更不能做成 Web 管理台。

2026 年 5 月的 desktop 实验已经证明：如果沿着“左栏 + 顶栏 + 面板 + 列表 + 状态徽标”的方式推进，即使颜色克制、组件统一，也会滑向精致后台，而不是字幕生产应用。

推荐视觉关键词：

- 字幕工作在前台。
- 主舞台明确。
- 辅助能力后退。
- 高密度但不后台化。
- 适合长时间检查和修改。
- 有明确画面意图，而不是组件堆叠。

必须避免：

- 常驻左栏导航作为默认骨架。
- 常驻顶栏导航作为默认骨架。
- 面板墙。
- 圆角卡片网格。
- 卡片嵌套卡片。
- Dashboard 统计块。
- 通用组件库审美。
- Linear、VS Code、Notion 或 SaaS 控制台式参考。

推荐方向是桌面应用主舞台：

- 一个主要工作面长期占据前台。
- 字幕行、时间轴、当前编辑、问题定位和输出状态成为第一视觉层。
- 服务接入、环境诊断、术语管理和导出设置优先作为浮层、抽屉、命令面板或任务级 modal 出现。
- 顶部状态只保留必要运行状态，不成为导航系统。
- 列表只在对象本身就是列表时出现，例如字幕行、术语条目、历史任务。

颜色上应使用：

- 中性色为主。
- 少量品牌强调色。
- 状态色只用于成功、警告、错误、处理中。

不要过度使用毛玻璃、强透明和大面积渐变。

毛玻璃可以用于欢迎页、空状态、浮层或视频预览上的字幕控制条，但不适合用于字幕列表、质量问题列表、日志、表格和编辑区。那些地方需要高可读性和长时间工作稳定性。

视觉实现必须先遵守 `../rules/FRONTEND_FAILURE_RECOVERY_RULES.md`。如果本节和失败后准则冲突，以失败后准则为准。

## 14. 前端工程原则

### UI 不直接绑定 CLI 参数

前端应该有自己的领域模型：

- `TaskDraft`
- `Task`
- `Segment`
- `SubtitleIssue`
- `TermEntry`
- `ProviderProfile`
- `EnvironmentCheck`
- `ExportPreset`

然后由 adapter 转成 worker 需要的 JSON。

不要让 React 表单字段直接等于 CLI 参数名。否则未来 worker 改参数，UI 会很难维护。

### 事件流是前端状态的一等来源

worker 的 JSONL 事件流对桌面前端很重要。

前端应该把事件流转成：

- 当前步骤。
- 当前进度。
- 时间线。
- 错误摘要。
- 可恢复状态。
- 日志详情。

不要只把事件当 console log。

### Artifact 要包装成用户入口

不要直接暴露完整工件目录树。

应该转成：

- 打开输出文件。
- 查看质量报告。
- 查看 ASR 诊断。
- 查看术语记忆。
- 查看 provider 调用记录。
- 打开任务目录。

高级用户可以打开目录，但普通用户应该先看到明确入口。

### 字幕列表必须考虑性能

真实字幕任务可能有几百到几千行。

结果检查界面需要：

- 虚拟列表。
- 快速搜索。
- 键盘快捷键。
- 问题跳转。
- 局部保存。
- 脏状态提示。

不要用普通表格硬撑。

### 所有长任务都要可取消、可恢复、可解释

任何长任务都应该有：

- 当前阶段。
- 当前动作。
- 取消按钮。
- 日志入口。
- 失败恢复入口。

恢复任务时要告诉用户：

> 会从已完成的工件继续，而不是从头开始。

## 15. 落地约束

本文件不定义阶段任务。无论第一阶段实现范围多小，前端都必须遵守这些约束：

1. 任务是产品中心对象，所有结果、日志、工件和恢复都围绕任务组织。
2. 字幕结果的真实来源是结构化字幕行，SRT、ASS、VTT 是导出视图。
3. 结果检查属于主流程，不是任务完成后的附属页面。
4. 质量问题必须可筛选、可跳转、可处理。
5. 术语记忆是项目资产，不是单个表单参数。
6. Provider 是服务连接体系，不是底层字段集合。
7. 翻译服务和 ASR 服务必须分开表达。
8. 保存和重新导出必须分开。
9. 失败状态必须解释原因、影响和下一步。
10. 普通用户界面不直接暴露 worker/CLI 内部概念。
11. 工件目录要包装成用户入口，高级用户再打开原始目录。
12. 所有长任务都必须可取消、可恢复、可解释。
13. 专业字幕编辑需要高密度、高可读性和键盘效率。
14. 视觉风格应克制、专业、安静，不应为了炫技牺牲可读性。
15. 禁止把产品做成通用后台、SaaS 控制台、圆角卡片网格或 Web 多页面管理台。

最小实现可以只填充一部分能力，但不能改变这些结构。正确的路径是：

> 先确认产品画面意图，再逐步填充能力。工程结构不能反过来决定设计。

## 16. 最终建议

TransVortex 的前端不应该长得像“一个模型调用面板”，也不应该长得像“一个视频上传转换器”。

它更应该像一个本地字幕生产工作台：

- 创建任务。
- 运行任务。
- 观察进度。
- 处理失败。
- 检查字幕。
- 修正问题。
- 管理术语。
- 重新导出。
- 沉淀项目资产。

这套方向能把已有 worker 能力真正产品化。

尤其是这三个核心体验最关键：

- 任务详情页。
- 结果检查工作台。
- 术语表工作区。

只要这三个核心体验做对，TransVortex 就会从“可视化 CLI”变成真正的桌面字幕生产工具。
