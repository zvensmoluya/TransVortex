# TransVortex 前端重设计功能说明

本文档面向 UI 设计师、交互设计师和产品协作者，用来说明 TransVortex 这个系统已经具备或正在形成的字幕生产能力，以及这些能力在前端中应如何被理解。它不是代码重构计划，也不是对当前 desktop 实现的验收清单。

当前桌面端只是一个快速迭代出来的实验性工作台，主要价值是验证 worker 能被可视化入口调用。它不代表最终产品形态，也不应该成为设计约束。真正应该约束设计的是：用户要完成什么任务、系统能提供什么能力、哪些概念需要被清楚表达。

## 1. 设计目标

前端重设计的目标不是“把现有 desktop 美化一下”，而是重新设计一个适合字幕生产工作流的桌面产品。

核心目标：

- 让用户能把本地视频或已有字幕转成高质量目标语言字幕。
- 让用户能清楚知道任务正在进行到哪一步、失败在哪里、下一步怎么处理。
- 让复杂的模型、ASR、术语记忆、字幕质量处理能力变成可理解的产品功能。
- 让高级能力保留入口，但不要让普通用户一开始就面对内部参数。
- 让结果检查、人工修改和重新导出成为自然流程，而不是隐藏在工件目录里。

设计时应优先从用户工作流出发，而不是从当前 React 页面、Tauri command 或 CLI 参数出发。

## 2. 产品定位

TransVortex 是一个本地字幕生产工具。它不是单纯的“视频转文字”，也不是只做文件格式转换。

它的主要价值链路是：

```text
输入视频/字幕
  -> 获取源语言字幕
  -> 翻译
  -> 使用术语记忆提升一致性
  -> 优化字幕可读性和时间轴
  -> 导出字幕文件
  -> 人工检查和再次导出
```

系统有三个入口层：

- CLI / worker：当前能力最完整，是系统真实能力的主要参考。
- desktop：当前只是实验性图形入口，功能覆盖不完整，交互也未定型。
- 未来 agent / 自动化入口：通过稳定 JSON/JSONL 协议调用 worker。

因此，本设计文档总结的是“系统功能”，不是“当前前端功能”。当前前端只在必要时作为参考，说明哪些能力已经试接过。

## 3. 目标用户与典型场景

### 普通字幕用户

这类用户希望尽量少配置，直接完成任务。

典型需求：

- 拖入视频，选择源语言和目标语言。
- 选择“本地识别”或“云端识别”。
- 选择翻译模型。
- 生成 SRT/ASS/VTT 字幕。
- 打开输出文件。
- 如果失败，知道缺什么依赖或 key。

### 高级字幕制作者

这类用户关心质量、术语一致性和人工修正。

典型需求：

- 使用已有字幕，不重新 ASR。
- 指定内置字幕轨。
- 配置项目背景、翻译风格、术语表。
- 查看质量问题，例如阅读速度过快、时间重叠、空译文。
- 手动编辑字幕行。
- 重新导出不同格式。
- 从任务中沉淀术语表。

### 开发者 / 模型调试用户

这类用户需要连接不同模型服务和兼容网关。

典型需求：

- 配置 provider、base URL、模型、鉴权方式。
- 保存和检查 API key。
- 测试连接。
- 设置主模型和备用模型。
- 调整请求映射、token 字段、reasoning 参数等专家配置。
- 通过日志和工件定位失败原因。

## 4. 系统主要能力

### 4.1 完整视频字幕任务

系统可以从视频输入开始，完成源字幕获取、翻译、质量处理和导出。

用户可理解的功能：

- 选择本地视频。
- 选择源语言和目标语言。
- 自动判断是否使用视频内置字幕轨。
- 没有合适字幕轨时运行 ASR。
- 翻译为目标语言。
- 可选生成双语字幕。
- 导出 SRT、ASS 或 VTT。

系统内部能力：

- 支持视频输入。
- 支持 SRT 输入，跳过 ASR 直接翻译。
- 支持从视频中提取文本字幕轨。
- 支持本地 faster-whisper ASR。
- 支持 OpenAI Transcriptions 形态的云端 ASR。
- 支持翻译 provider routing 和 fallback。
- 支持可恢复任务、取消任务、查询状态和事件流。

设计重点：

- 对普通用户，应呈现为“创建字幕任务”。
- 对高级用户，允许展开字幕来源、ASR、翻译和输出配置。
- 不应要求用户理解 `input_type`、`source_mode`、`checkpoint` 等实现概念。

### 4.2 源字幕获取

系统的第一步是得到源语言字幕，也就是后续翻译的输入。

可能来源：

- 视频内置文本字幕轨。
- 本地 ASR。
- 云端 ASR。
- 用户提供的 SRT。
- 用户提供的 segments 文件，当前主要是 CLI 能力。

前端应表达的概念：

- 自动选择：如果视频有匹配语言的文本字幕轨，优先使用；否则识别音频。
- 强制识别：忽略视频内置字幕，直接运行 ASR。
- 使用内置字幕：选择视频中的某条文本字幕轨。
- 使用已有字幕：上传或选择 SRT。

需要避免的误解：

- 图形字幕轨不能像文本字幕一样直接翻译。
- 云端 ASR provider 和翻译模型 provider 不是同一回事。
- ASR prompt 是给语音识别的提示，不是翻译风格。

### 4.3 ASR 能力

ASR 是把音频转成源语言字幕。

本地 ASR：

- 使用 faster-whisper。
- 可选择设备，例如 CPU、CUDA 或自动。
- 可选择模型大小和计算精度。
- 更适合隐私、本地可控和已具备硬件的用户。

云端 ASR：

- 当前主要适配 OpenAI Transcriptions API。
- 默认模型可以是 `whisper-1`。
- 支持音频切片上传。
- 支持静音边界切分、并发上传、重试和失败后细分。
- 会保存原始响应和质量诊断，便于排查。

ASR prompt：

- 用来提示专有名词、角色名、作品名、术语、语音上下文。
- 可保存为 profile。
- 可限制最大字符数。
- 可选择是否拼接上一段 transcript。

设计重点：

- 普通模式只需要“本地识别 / 云端识别 / 自动”。
- 专业模式再提供模型、设备、chunk、prompt profile 等设置。
- ASR 质量应能在结果页查看，例如识别为空、疑似幻觉、重复字符、异常高 CPS。

### 4.4 翻译能力

系统可以把源字幕翻译成目标语言。

用户可理解的功能：

- 选择目标语言。
- 选择翻译模型。
- 选择翻译风格。
- 输入项目背景。
- 输入额外风格要求。
- 使用术语表保证专名和称谓一致。

系统内部能力：

- 支持多 provider。
- 支持主模型和 fallback 模型。
- 支持上下文窗口。
- 支持 capacity-aware 大 chunk 翻译。
- 支持翻译输出校验。
- 支持格式修复。
- 支持失败时 adaptive split。
- 支持 provider 调用指标和事件记录。

设计重点：

- 翻译设置要用自然语言表达，例如“自然字幕”“直译”“本地化”“学习辅助”。
- “项目背景”和“风格要求”应有清楚区别：
  - 项目背景：作品、人物关系、语境。
  - 风格要求：口吻、压缩偏好、是否保留粗口、是否避免解释性长句。
- 固定译名和术语不应该主要写在 prompt 里，而应进入术语表。

### 4.5 术语记忆

术语记忆是系统的重要能力，用来提升长视频、剧集、系列内容中的一致性。

用户可理解的概念：

- 项目术语表：用户维护或选择的专名、称谓、固定译法。
- 自动提取术语：系统在翻译前从全片源字幕中提取可能重要的术语。
- 翻译时遵循术语：把相关术语注入当前翻译上下文。
- 翻译后检查一致性：找出可能违反术语表的字幕行。
- 从任务沉淀术语表：把运行中形成的术语导出成可复用 preset。

系统内部能力：

- 加载 preset 术语表。
- 生成运行时术语库 `translation_memory.json`。
- 将术语按相关性注入翻译 prompt。
- 可选动态维护 memory patch。
- 合并和检查术语一致性。
- 从 segments/SRT bootstrap 术语 preset。
- 从任务 runtime memory 导出 preset。

设计重点：

- 不建议把 `bootstrap`、`inject`、`patch` 直接作为主界面文案。
- 推荐把术语记忆设计成独立工作区，而不是只在任务表单里填一个 preset id。
- 术语状态需要人类可理解：
  - proposed：系统建议，待确认。
  - confirmed：已确认。
  - locked：强制固定，不应被自动覆盖。

### 4.6 字幕质量处理

系统不仅翻译文本，还会处理字幕可读性。

质量维度：

- 译文是否为空。
- 时间轴是否重叠。
- 开始/结束时间是否合法。
- 阅读速度是否过快。
- 单行宽度是否过长。
- 行数是否过多。
- 持续时间是否过短或过长。
- 字幕间隔是否过小。
- 双语字幕是否过于拥挤。
- 输出格式是否存在交付风险。

系统能力：

- 字幕质量检查。
- 保守或均衡的质量优化。
- 模型压缩过长字幕。
- reflow 字幕窗口。
- delivery report，检查 SRT/ASS/VTT 输出质量。

设计重点：

- 结果页应按问题筛选和跳转。
- 质量问题应转化为用户能理解的提示，例如“阅读速度过快”，而不是只显示内部 code。
- 自动优化和手动编辑之间要有清楚边界。

### 4.7 输出和重新导出

系统支持多种字幕输出格式。

输出格式：

- SRT：通用字幕格式，适合大多数播放器和审稿。
- ASS：表现型字幕，支持样式、双语层级、安全区和更丰富排版。
- VTT/WebVTT：网页字幕格式。

系统能力：

- 从结构化 Segment 渲染不同格式。
- 支持单语和双语字幕。
- 支持双语顺序。
- 支持尽量保持单行。
- 支持任务完成后重新导出。
- 支持人工编辑结果后重新导出。

设计重点：

- 输出格式最好设计成多选，而不是 `both` 这种内部值。
- 应显示每个输出文件的路径和打开按钮。
- 编辑后要提醒用户“已修改但尚未重新导出”。
- ASS 样式和预览可以作为后续高级能力。

### 4.8 结果检查和人工编辑

结果检查是桌面产品的关键体验，不应只是附属功能。

系统能力：

- 打开任务最终 segments。
- 显示每条字幕的原文、译文、开始时间、结束时间。
- 显示 provider/model/chunk 信息。
- 显示基础问题和质量报告问题。
- 保存编辑后的 segments。
- 重新导出字幕。
- 打开术语记忆、reflow log、输出文件等工件。

理想前端能力：

- 字幕列表。
- 当前字幕详情。
- 时间轴概览。
- 按问题筛选。
- 上一条/下一条问题。
- 修改原文、译文和时间轴。
- 保存修改。
- 重新导出。
- 对照输出预览。
- 可选视频/音频辅助预览。

设计重点：

- 专业字幕工作流需要高效检查大量行，不能只有普通表格。
- 时间轴、问题列表和字幕编辑需要联动。
- 保存和导出是两个不同动作，应明确状态。

### 4.9 Provider、模型和凭据

系统支持可配置翻译模型 provider。

用户可理解的概念：

- 服务商连接：例如 OpenAI、Anthropic、Google 或兼容网关。
- 模型：某个服务商下具体使用的模型。
- API key：连接服务商所需凭据。
- 模型路由：默认模型和失败备用模型。

系统能力：

- provider preset。
- protocol template。
- 自定义 base URL。
- 多种鉴权方式。
- request/response mapping。
- 拉取模型列表。
- 最小联网测试。
- 零 token 协议预检。
- 保存 provider 到 `providers.local.yaml`。
- 保存 key 到用户级 `~/.transvortex/auth.json`。
- 设置 primary/fallback 路由。
- 防止并发覆盖 provider 配置。

设计重点：

- 普通用户应优先看到“选择服务商、粘贴 key、选择模型、测试连接”。
- 专家用户再进入 base URL、endpoint、mapping、headers、token 字段等配置。
- API key 保存位置要说清楚：默认是用户级凭据文件，不是项目 `.env`。
- 翻译 provider 和 ASR provider 需要视觉上区分。

### 4.10 任务管理和可恢复性

系统任务是可恢复、可查询和可取消的。

系统能力：

- 任务有唯一 `task_id`。
- 每个任务有稳定工件目录。
- 任务状态会持续更新。
- 事件以 JSONL 保存。
- checkpoint 支持恢复。
- 用户可以请求取消。
- 失败任务可以恢复。
- 历史任务可列出。

前端应表达：

- 当前任务进行到哪一步。
- 当前步骤正在做什么。
- 已完成多少。
- 是否可以取消。
- 失败后能否恢复。
- 恢复会从已完成工件继续，而不是总是从头开始。
- 任务输出和工件在哪里。

设计重点：

- 应有独立任务详情页。
- 任务历史不应只是列表，还要支持检查、打开输出、恢复、查看错误。
- 错误提示要连接到恢复或配置动作。

## 5. 建议前端信息架构

这是给设计的建议，不是现有代码结构。

### 5.1 一级导航

建议一级导航：

- 新建任务
- 任务历史
- 结果检查
- 术语表
- 模型与凭据
- 环境诊断
- 设置

如果希望更偏向工作流，也可以把“结果检查”合并进任务详情中，通过历史任务进入。

### 5.2 新建任务

建议设计成清晰流程，而不是一个巨大的参数表。

步骤建议：

1. 选择输入
   - 视频。
   - SRT。
   - 后续可扩展 segments。
2. 选择任务类型
   - 视频转写并翻译。
   - 只生成源字幕。
   - 翻译已有字幕。
   - 只导出已有结果。
3. 设置语言和字幕来源
   - 源语言。
   - 目标语言。
   - 自动/ASR/内置字幕。
   - 字幕轨选择。
4. 设置模型
   - 翻译模型路由。
   - ASR 方式。
   - key 状态。
   - 运行前检查。
5. 设置翻译要求
   - 项目背景。
   - 风格。
   - 术语表。
6. 设置输出
   - 格式多选。
   - 单语/双语。
   - 双语顺序。
   - 输出目录。
7. 启动前摘要
   - 输入。
   - 处理方式。
   - 模型。
   - 输出格式和位置。
   - 可能阻塞的问题。

### 5.3 任务详情

任务详情应是用户理解进度和处理失败的核心界面。

建议包含：

- 任务标题、状态、输入文件、输出文件。
- 流程步骤条。
- 当前正在处理的步骤。
- 当前模型/ASR/provider 信息。
- 进度和剩余工作。
- 错误、警告和下一步建议。
- 事件日志。
- 工件入口。
- 输出文件入口。
- 取消、恢复、重新导出等操作。

### 5.4 结果检查

建议把结果检查设计成专业字幕检查界面。

建议区域：

- 字幕列表。
- 当前行编辑器。
- 质量问题列表。
- 时间轴概览。
- 输出预览。
- 术语一致性提示。
- 重新导出设置。

最小可用能力：

- 搜索字幕。
- 按问题筛选。
- 快速跳转上一条/下一条问题。
- 编辑原文、译文、时间。
- 保存。
- 重新导出。

### 5.5 术语表

建议新增独立术语表工作区。

建议能力：

- 查看 preset 列表。
- 查看术语条目。
- 新建、编辑、删除条目。
- 标记 proposed/confirmed/locked。
- 从任务自动生成术语草稿。
- 从任务运行时术语库导出 preset。
- 查看一致性问题。
- 跳转到相关字幕行。

### 5.6 模型与凭据

建议拆成普通配置和专家配置。

普通配置：

- 服务商 preset。
- API key 保存状态。
- 模型选择。
- 测试连接。
- 主模型和备用模型。

专家配置：

- base URL。
- endpoint。
- auth 方式。
- request mapping。
- response mapping。
- token 字段。
- provider limits。
- 自定义 JSON provider。

ASR 服务配置应和翻译 provider 分开，避免用户误解。

### 5.7 环境诊断

环境诊断应从“检查报告”变成“问题修复入口”。

建议能力：

- 显示 Python、ffmpeg、ffprobe、faster-whisper、provider key、artifacts 权限状态。
- 对每个失败项给下一步。
- 区分阻塞和非阻塞问题。
- 从缺 key 直接跳转到凭据配置。
- 从缺 provider 直接跳转到模型配置。

## 6. 关键对象和状态

设计不需要暴露这些内部对象名，但需要理解它们承载的信息。

### 任务

任务记录包含：

- 任务 ID。
- 输入文件。
- 源语言和目标语言。
- 是否双语。
- 当前状态。
- 创建和更新时间。
- 输出文件路径。
- 错误信息。
- 运行设置。

### 事件

事件记录任务过程：

- 阶段变化。
- 进度更新。
- provider 调用尝试。
- 警告。
- 错误。
- 完成。
- 取消。
- 编辑和重新导出。

前端可以把事件转成时间线、日志、当前动作和错误提示。

### 字幕行

字幕行包含：

- ID。
- 开始时间。
- 结束时间。
- 原文。
- 译文。
- 质量问题。
- 来源 provider/model/chunk。

前端结果检查应围绕字幕行组织。

### Provider

Provider 包含：

- 名称。
- 协议。
- base URL。
- 模型列表。
- 凭据状态。
- endpoint 和 mapping。
- 能力限制。

前端普通模式只需要展示其中一小部分。

## 7. 任务工件

系统会为每个任务保存工件目录。设计上不一定要直接暴露完整目录树，但可以把它们转化为用户入口。

重要工件类型：

- 任务信息。
- checkpoint。
- 事件日志。
- 抽取音频和媒体信息。
- ASR 原始结果。
- 源字幕。
- 翻译结果。
- 翻译校验和修复记录。
- 最终字幕 segments。
- 字幕质量报告。
- 术语记忆。
- 输出字幕文件。

可设计入口：

- 打开输出文件。
- 打开任务目录。
- 查看日志。
- 查看 ASR 诊断。
- 查看质量报告。
- 查看术语记忆。
- 查看 provider 调用诊断。

## 8. 当前 desktop 的参考价值

当前 desktop 已经验证了以下事情：

- Tauri 可以启动 Python worker。
- 可以接收 JSONL 事件并展示进度。
- 可以选择文件、打开目录和输出文件。
- 可以配置 provider、保存 key、测试连接。
- 可以启动任务、取消任务、恢复任务。
- 可以列出历史任务。
- 可以打开结果、编辑字幕行并重新导出。

但当前 desktop 不应被视为最终设计基准：

- 页面分组不代表最终信息架构。
- 表单字段不代表最终用户概念。
- 当前文案不代表最终产品语言。
- 当前交互不代表用户被约束过的需求。
- 当前代码组织不属于本设计文档需要解决的问题。

设计可以完全重构现有界面，只要继续调用同一套 worker 能力即可。

## 9. 前端落地顺序

本节定义阶段实现顺序，不定义产品终局。产品终局和不可妥协的体验边界以 `核心方向.md` 为准。

阶段拆分的原则是：

> 先搭终局骨架，再逐步填充能力。

第一阶段不应该为了“最小实现”把产品做成上传表单、日志窗口和下载按钮。即使能力覆盖有限，也应先建立任务、结果检查、术语表、服务连接、环境诊断这些长期结构。

### 9.1 第一阶段：把已有核心能力产品化

第一阶段的目标不是新增更多 worker 能力，而是把现有能力组织成可理解、可操作、可恢复的前端工作流。

必须优先打通的主链路：

```text
新建任务 -> 运行任务 -> 查看进度/失败 -> 检查结果 -> 编辑字幕 -> 保存 -> 重新导出
```

建议优先实现：

- 新建任务流程：输入、语言、字幕来源、模型、术语表、输出格式、启动前检查。
- 任务历史和任务详情：状态、阶段、事件时间线、输出文件、工件入口。
- 长任务反馈：当前步骤、进度、取消、错误、恢复入口。
- 失败解释：失败阶段、影响、是否可恢复、推荐操作、日志入口。
- 结果检查：字幕行列表、质量问题筛选、上一条/下一条问题、当前行编辑。
- 保存和重新导出：明确区分未保存、已保存待导出、已重新导出、导出失败。
- 模型与凭据普通配置：服务商、API key 保存状态、模型选择、连接测试、主模型和备用模型。
- 翻译服务和 ASR 服务分开表达。
- 环境诊断：阻塞问题、质量风险、可选增强，以及对应修复入口。
- 输出文件管理：显示 SRT、ASS、VTT 路径、更新时间、打开和重新导出入口。

术语能力在第一阶段不能缺席，但可以先做核心闭环：

- 选择术语表。
- 查看任务使用的术语。
- 导入和导出术语表。
- 查看自动提取的术语建议。
- 确认建议项。
- 区分系统建议、已确认、强制固定。
- 在结果检查页显示术语命中或疑似不一致。
- 重新导出时继续使用已确认术语。

Provider 能力在第一阶段也不能缺席，但应优先服务主流程：

- 配置翻译服务。
- 配置 ASR 服务。
- 保存 API key 到用户级凭据。
- 测试连接。
- 选择默认模型。
- 设置备用模型。
- 在任务失败时说明是否是服务连接问题。

### 9.2 第一阶段只保留入口的能力

以下能力是核心方向的一部分，但第一阶段可以先提供入口、占位、折叠高级面板或只读查看，不必一开始做成完整专家系统：

- provider request/response mapping 可视化编辑。
- 任意 headers 编辑器。
- token 字段映射。
- reasoning 参数全集。
- fallback 策略图形化编排。
- provider schema 高级调试面板。
- ASR prompt profile 管理。
- ASS 样式可视化编辑器。
- 视频预览和波形时间轴。
- 术语版本历史。
- 多项目术语库治理。
- 术语冲突批量合并、去重和批量修复。
- 多任务批处理。
- 任务工件清理和批量删除。

这些能力不能反过来改变信息架构。例如，第一阶段即使没有完整术语资产管理，也应该把术语表放在项目资产的位置，而不是退化成新建任务表单里的一个隐藏参数。

### 9.3 后续增强方向

后续阶段应围绕专业字幕工作台继续增强：

- 视频/音频预览。
- 波形时间轴。
- ASS 样式可视化编辑。
- 术语一致性批量修复。
- ASR prompt profile 管理。
- 多任务批处理。
- 任务工件清理。
- 字幕烧录或本地播放模式。
- provider 专家配置和调试工具。
- 跨任务术语沉淀和项目资产管理。

这些增强应服从核心方向：任务是中心对象，结果检查是主流程，术语是资产，Provider 是服务连接体系。

## 10. 不建议作为设计约束的内容

以下内容是实现细节，不应直接约束 UI：

- 当前 React 组件结构。
- 当前 `main.tsx` 的页面划分。
- 当前表单字段名称。
- CLI 参数名。
- Python 模块名。
- Tauri command 名。
- artifact 目录的完整层级。
- `memory bootstrap/inject/patch` 这类内部开关名。
- `compat_mode`、`request_mapping`、`response_mapping` 这类 provider 内部术语。

这些内容可以影响专家模式和开发者文档，但不应成为普通用户界面的主语言。

## 11. 需要优先讨论的产品问题

以下问题会影响设计方向，建议在正式设计前先确认：

- 桌面端第一屏是“新建完整字幕任务”，还是提供“转写 / 翻译 / 导出”多任务入口？
- 术语表是否是主导航中的独立模块？
- 结果检查是否需要内置视频预览或音频波形？
- 输出格式是否改成多选，替代当前 `both` 概念？
- 普通用户是否需要看到 provider 专家配置？如果需要，入口如何隐藏但可发现？
- ASR 云端服务是否单独设计 provider 管理，还是先保留 OpenAI Transcriptions 简化配置？
- 恢复任务时，用户是否可以修改模型、字幕质量、输出格式等设置？
- 是否需要任务删除、清理工件和批量管理？这会涉及误删确认和数据安全。
- 术语记忆中的 proposed/confirmed/locked 是否需要用户可编辑？
- 当前 desktop 是否要继续作为开发工作台保留，还是下一版直接替换为新信息架构？
